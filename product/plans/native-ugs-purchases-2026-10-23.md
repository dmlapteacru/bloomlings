# .NET Android, UGS и интерфейс покупки

Дата: 2026-10-23. Продолжение [игрового интерфейса аккаунта](account-in-game-ux-2026-10-22.md) и [серверной экономики](../../backend/economy/README.md).

## Путь подключения текущего APK

Текущий APK — .NET Android (`playtest/android`), а не Unity Player. Для вызова UGS Cloud Code переносить этот интерфейс в Unity не требуется: добавлен engine-free `UgsHttpEconomyTransport`, который компилируется непосредственно в .NET Android и настольный рендерер через `playtest/OnlineServices.props`.

Транспорт использует player REST API:

- `POST https://cloud-code.services.api.unity.com/v1/projects/{projectUuid}/scripts/ExecuteEconomy`;
- заголовок `Authorization: Bearer <UGS player access token>`;
- тело `{ "params": { "action": "read|execute", "expectedOwnerId": ..., ... } }`;
- ответ сервиса `{ "output": <ответ ExecuteEconomy> }`.

Формат сверялся с генерированным кодом пакета Cloud Code в [зеркале пакета Unity, commit cc6db53](https://github.com/needle-mirror/com.unity.services.cloudcode/tree/cc6db53e0bc10ee6392bdf506a1400e79e364bdc/Runtime/com.unity.services.cloudcode.internal): `Apis/CloudCodeApiRequests.cs`, `Models/RunScriptArguments.cs`, `Models/RunScriptResponse.cs`. Это сверка исходников и проверки через in-memory HTTP handler; **не успешный запрос к live UGS**. В облачной среде UGS-домены не разрешены, project/session пользователя не настроены.

Токен должен предоставлять будущий нативный провайдер PGS → UGS Authentication. Наличие адаптера не создаёт такую авторизацию. `UgsPlayerSession` хранит токен только в памяти; на смене/обновлении сессии увеличивает epoch, сеть не меняет владельца. Выбор UGS environment относится к авторизации, а не к произвольному полю покупки. Нельзя использовать сервисный/admin secret в APK или считать LocalPlayerId backend-владельцем.

Сетевой код не использует UnityEngine или Unity SDK. URL фиксирован на UGS, перенаправления выключены в стандартном HttpClientHandler, TLS-проверки остаются стандартными. Один вызов — одна попытка HTTP, timeout 20 секунд, ответ ограничен 1 МиБ. Нет автоматического HTTP retry, логирования токенов/тел/чеков или обновления чужого профиля по позднему ответу.

## Что изменилось в самой игре

Все существующие точки покупки .NET клиента используют один `PurchasePanel`: гардероб, магазин бустеров/анимаций, аватары и покупка бустера в уровне. Арт, зелёная кнопка с петалями и компоновка карточки сохранены; пояснение вмещает две строки.

- До получения цены нельзя подтвердить покупку.
- Кнопка блокируется на время запроса; повторный тап не отправляет вторую операцию.
- При отсутствии сети новая покупка не вызывается. Нативный Android-хост проверяет Internet + Validated network; результат кэшируется на 250 мс, чтобы не делать системные IPC-запросы на каждом UI-чтении. Каталог/примерка/выбор купленной вещи остаются локальными.
- При неопределённом ответе показывается Check purchase, без кнопки повторной покупки. Закрытие окна не означает отмену уже отправленного запроса.
- Изменение цены обновляет сумму в карточке и требует нового нажатия.
- Старый ответ не закрывает окно другого товара и не подтверждает другую сессию.
- Локальные dev-покупки возвращают явный успех/отказ. Нормальный возврат из callback с отказом больше не считается успешной покупкой.
- Метаданные товаров в PurchaseOffer содержат тип и ID; локальная цена перечитывается из текущего источника перед подтверждением, а не берётся навсегда из исходной карточки.

Тестовые состояния для PNG находятся только в рендерере, не в APK: offline, loading, pending, новая цена, отказ. В игре нет переключателей фальшивой сети/покупок.

## Связь с журналом серверных операций

`OnlinePurchaseOperation` реализует тот же UI-контракт поверх `OnlineEconomyClient`. Он не содержит callback локальной траты и никогда не вызывает её после сетевой ошибки. Успех выводится только из ACK нужного sequence с `ok=true`, а баланс — из целого подтверждённого снимка.

При неизвестном результате повторяется точная строка исходной операции с прежними installationId/sequence. Перезапуск приложения восстанавливает её из журнала. Запрос другого товара не заменяет ожидающую покупку. Непосланная покупка/новая цена требуют подтверждения; проверка статуса не даёт такого согласия. Объект операции привязан к исходной сессии уже при создании: смена epoch между нажатием и первым шагом coroutine не может использовать старое согласие.

`DesignApp.OnlineRoutines` исполняет эти coroutines на UI-потоке, с ограниченным числом немедленных шагов за кадр. `ShowPurchase` принимает IPurchaseOperation и не вызывает локальную покупку. Для серверного сценария хост создаёт OnlinePurchaseOperation с этим runner **после согласованной миграции read model/наград/трат**.

## Что ещё требуется перед live-включением

Сейчас обычный APK остаётся на своей локальной dev-экономике. Присутствие REST-класса, сети или projectId не переключает кошелёк автоматически. Ни средства пользователя, ни данные UGS этим коммитом не менялись.

До включения нужны:

1. Нативный PGS/UGS Authentication provider, сохранение/восстановление сессии средствами платформы и явная миграция гостя к владельцу.
2. Настроенные UGS project/environment, безопасный bootstrap economy_v1 и доверенные выдаватели доказательств побед/рекламных наград.
3. Единый серверный read model во всех местах и миграция всех наград/трат (daily, milestones, ads, billing и бустеры). Нельзя оставить локальные награды и включить только серверную кнопку Buy.
4. Постоянная точка возврата к незавершённой покупке в server-mode host; текущий descriptor PendingPurchase даёт её тип/товар/sequence. Закрытие UI намеренно сохраняет outbox. Явная отмена ещё не исполненной серверной операции с безопасным завершением её sequence остаётся отдельным протоколом; нельзя просто удалять запрос или отматывать sequence после таймаута.
5. Реальная проверка Android-сборки/устройства, авторизации, REST endpoint и store billing. Покупки за реальные деньги этим изменением не включались.

Состояния pending/reprice готовы в игровой карточке и проверены с настоящим клиентским журналом и тестовым сервером. В обычной локальной сборке без backend-сессии эти серверные состояния не имитируются.
